# LoopSplat 策略集成阶段性报告

> 2026年6月11日

---

## 1. 项目概述

本项目在 LoopSplat（3DV 2025）的基础上集成了三项策略。第一项和第二项来自 GI-SLAM 论文（arXiv:2503.18275），分别是 IMU 损失函数和 Gaussian Visibility 动态关键帧选择。第三项来自 Photo-SLAM 论文（CVPR 2024），是 Gaussian Pyramid 多尺度渐进训练。三项策略默认全部关闭，可独立或组合使用。目标是通过完整的消融实验验证各项策略的单独贡献和组合效果，作为学术论文的核心实验部分。

其中 IMU 损失函数（以下简称 S1）作用于跟踪阶段。它在视觉优化的基础上增加了 IMU 加速度和角速度的物理约束——用牛顿运动学积分预测帧间运动，与视觉估计的结果求差作为额外的损失项。这个策略需要数据集包含 IMU 传感器数据，在本次实验中仅在 AzureKinect 和 FM 数据集上测试。

Gaussian Visibility 关键帧选择（以下简称 S2）作用于帧筛选阶段。它不再按固定帧间隔决定哪些帧做关键帧，而是每帧实时评分：当前帧看到的高斯点与最近关键帧的差异越大、移动距离越远，得分越高；运动模糊的帧扣分。得分超过阈值的才选为关键帧。为防止极端情况下模型退化，30 帧无关键帧时强制插入一帧。

Gaussian Pyramid 多尺度训练（以下简称 S3）作用于建图阶段。对每张关键帧构建三层图像金字塔——四分之一分辨率、二分之一分辨率和全分辨率，训练从最粗层开始，每被选中八次自动升级一层。低分辨率下每个高斯覆盖更大像素区域，快速学习全局结构；高分辨率下精细优化纹理。这个策略只改变渲染时的分辨率和对比用的真实图像分辨率，不修改高斯模型本身。

## 2. 实验设计

实验采用三个数据集共四十四组实验的完整消融设计。

A 组使用 TUM RGB-D 数据集，这是标准的 SLAM 评估基准。该数据集包含真实位姿标签但没有 IMU 数据，因此只能测试 S2 和 S3 两项策略。选取了五个具有代表性的场景：办公桌场景 freiburg1_desk、第二个办公桌 freiburg1_desk2、房间场景 freiburg1_room、大范围空间运动场景 freiburg2_xyz 和长走廊场景 freiburg3_long。每个场景跑四种配置：纯基线、单独开 GI-KF、单独开 Pyramid、两者同时开。A 组共计二十个实验，同步评估轨迹精度 ATE 和渲染质量 PSNR/SSIM/LPIPS/Depth L1。

B 组使用自采集的 Azure Kinect DK 数据集，拍摄场景为学生实验室环境，帧率五 FPS，分辨率 720p，同时采集了 IMU 数据且包含真实位姿标签。因为具备 IMU，B 组可测试全部三项策略。B 组包含一个场景、六种策略配置：基线、单独开 IMU、单独开 GI-KF、单独开 Pyramid、GI-KF 加 Pyramid、三项全开。B 组共计六个实验，评估指标与 A 组相同。

C 组使用公开的 FM 数据集，同样是 Azure Kinect DK 在真实室内环境中采集，包含宿舍和酒店等不同房间类型，全部选择快速运动模式。FM 数据集包含 IMU 数据但没有真实位姿标签，因此仅评估渲染质量指标。C 组选取了三个代表性场景：dorm1_fast1（学生宿舍快速移动）、dorm2_fast（第二间宿舍）、hotel_fast1（酒店房间）。每个场景与 B 组一样跑六种策略配置，共计十八个实验。

在实验命名上，每个实验由场景编号加策略后缀组成。比如 A1_0 是 TUM freiburg1_desk 基线，B1_5 是 AzureKinect 三项全开，C1_2 是 FM dorm1_fast1 单独开 GI-KF。

## 3. 当前进展

A 组二十个实验全部完成。B 组六个实验全部完成。C 组十八个实验中，C1 场景的六个配置已全部完成（含 C1_2 的异常情况，见下文），C2 场景完成了六个配置中的三个（已跑完 Baseline、IMU、GI-KF），C3 场景尚未开始。

A 组实验均在本地 GPU 服务器上完成，单个 TUM 场景四个实验的总耗时约四十分钟。B 组实验在租用 GPU 服务器上完成，单个实验约十五分钟。C 组因数据量较大（dorm1_fast1 就有八百六十九帧）且存在 loop closure 的 GSR 配准开销，单个实验耗时约一小时以上。目前 C 组仍在租用服务器上持续推进。

## 4. C1_2 的特殊情况

C1_2（FM dorm1_fast1 场景，单独使用 GI-KF）出现了预期之外的现象：该实验生成了七十二个子图，而同一场景的其他配置仅生成十七个左右。

经过排查，根因是 GI-KF 单独使用时选取的关键帧更少，导致高斯模型的全局优化不充分，视图覆盖不足。这使得跟踪模块在进行相机位姿估计时产生了更大的漂移，连续帧间的累积平移和旋转更快达到了 motion heuristic 的子图切割阈值。子图被频繁切分后，每次切分子图都要触发一次完整的 loop closure 流程——构建所有已存在子图的位姿图、检测闭环、对检测到的闭环进行 GSR 精密配准。七十二个子图意味着六十多次完整的位姿图构建和配准循环，每次都要遍历大量子图对。即使代码层面已做了子图数据缓存和 GSR 迭代数优化，六十多次 construct_pose_graph 调用本身的计算量仍然远超正常情况。

我们加入的安全网机制（连续三十帧无关键帧时强制插入一帧）并未触发，说明该场景下 GI-KF 本身选帧是正常的，问题出在选帧之后引发的模型精度下降和位姿漂移这一链条上。

该现象的一个重要验证来自 C2_2——C2 是 FM 数据集不同房间的 dorm2_fast 场景，同样使用了 GI-KF 策略且同样无 Pyramid。C2_2 的子图数保持在十七个左右，运行正常。这说明 GI-KF 的跟踪退化不是所有场景都会发生的系统性缺陷，而是场景依赖的。C1_4（同一场景，GI-KF 加 Pyramid 同开）也正常运行，证明 Pyramid 的多尺度训练能有效补偿 GI-KF 单独使用时的模型泛化不足。

这一发现对论文有积极意义：它揭示了三项策略之间的互补关系，尤其是 Pyramid 对 GI-KF 的支撑作用。我们建议在论文中以 C1_2 的现象作为案例，用 C2_2 的正常结果和 C1_4 的正常结果来论证 GI-KF 应配合 Pyramid 联合使用以确保健壮性。

关于 C1_2 本身的实验执行，目前留给作者自行决定——用更大的超时自然跑完、跳过该实验并在论文中标注计算不可行、或者将其作为特别案例在论文中单独讨论。

## 附录：代码修改概要

本次项目在 LoopSplat 原始代码基础上共修改和新增了约二十个文件，涉及策略实现、数据集适配、实验管理和故障修复四方面。

策略实现方面，GI-KF 关键帧选择在 mapper_utils.py 中新增了五个计算高斯可见性的工具函数，并在 gaussian_slam.py 中新增了两个方法（评分函数和关键帧注册函数）并修改了主循环流程，配置文件新增了 keyframing 配置段。Pyramid 多尺度训练在 mapper_utils.py 中新增了四个金字塔构建工具函数，在 mapper.py 中修改了 map 和 optimize_submap 两个方法实现按分辨率级别逐步训练的逻辑，配置文件新增了 gaussian_pyramid 配置段。

数据集适配方面，新增了整个 datasets_fm.py 实现了 FM 数据集的加载，包括时间戳解析、IMU 数据读取和图像关联。在 datasets.py 中注册了 fm_dataset 分支。新建了四个 FM 场景配置文件。

实验管理方面，编写了 run_ablation.py 自动化运行全部四十四组实验，支持断点续跑、单实验运行和分组运行。编写了 aggregate_results.py 自动扫描输出目录并生成 Markdown 对比表格。编写了三份文档：GI-SLAM 策略集成指南、Photo-SLAM 策略集成指南和完整消融实验运行指南。

故障修复方面，修复了 TUM RGB-D 数据集在 loop closure 的 submap_loader 中因缺少 get_processed_image_paths 方法导致的崩溃，以及后续的 Camera 尺寸不匹配和图片加载格式不一致问题。修复了评估器在无 submaps 目录或无真值位姿时的空值保护。修复了 FAISS 在 GPU 显存不足时的降级处理。修复了 evo 库在无图形界面的服务器上因 Qt5Agg 后端导致的启动崩溃。优化了 loop closure 中 construct_pose_graph 重复从磁盘加载全部子图的问题，通过加入子图数据缓存机制将磁盘读取和图片加载从多次降到一次。
