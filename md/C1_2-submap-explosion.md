# C1_2 子图爆炸现象分析报告

> 日期：2026-06-09  
> 涉及实验：C1_2（FM dorm1_fast1, +GI-KF）  
> 现象：SLAM 主循环中生成 74 个子图（正常应 ~17 个），后续 loop closure 无法在合理时间内完成

---

## 1. 现象描述

| 实验 | 策略 | 子图数 | mapping_vis 最后帧 | 状态 |
|------|------|--------|-------------------|------|
| C1_0 | Baseline | ~17 | 869 | ✅ 正常完成 |
| C1_1 | +IMU | ~17 | 869 | ✅ 正常完成 |
| **C1_2** | **+GI-KF** | **74** | 860 | ❌ SLAM 完成后卡在 loop closure |
| C1_3 | +Pyramid | ~17 | 869 | ✅ 正常完成 |
| C1_4 | +KF+Pyramid | ~17 | 869 | ✅ 正常完成 |
| C1_5 | +ALL | ~17 | 869 | ✅ 正常完成 |

仅 C1_2（GI-KF 单独开启）出现异常，其余策略均正常。

---

## 2. 根因分析

### 2.1 因果链

```
GI-KF 动态选帧 → 更少的关键帧做建图
    │
    ▼
高斯模型优化不充分（关键帧少 → optimize_submap 只覆盖了部分视角）
    │
    ▼
Tracker 位姿漂移增大（模型差 → 渲染与 GT 匹配困难 → 位姿估计噪声大）
    │
    ▼
连续帧间累计位移更容易达到 motion heuristic 阈值 (rot_thre=50°, trans_thre=0.5m)
    │
    ▼
子图边界频繁触发 → 74 个子图（正常 ~17 个）
    │
    ▼
74 次 loop closure 触发 × construct_pose_graph(74 个子图)
→ GSR 配准指数级膨胀 → 无法在合理时间内完成
```

### 2.2 为什么 C1_4（+KF+Pyramid）不会这样

| 对比维度 | C1_2 (+GI-KF) | C1_4 (+KF+Pyramid) |
|---------|---------------|-------------------|
| 关键帧数 | 较少 | 相同（GI-KF 决定） |
| 高斯模型质量 | 差（全分辨率训练，关键帧少 → 覆盖不足） | 好（Pyramid 粗到细训练 → 泛化更好） |
| 跟踪精度 | 差（模型差 → 位姿漂移） | 好（模型好 → 位姿准） |
| 子图数 | 74 | ~17 |

Pyramid 通过粗到细渐进训练，使得即使关键帧较少，高斯模型也能较好地覆盖场景（低分辨率下每个高斯覆盖更大区域 → 泛化更强）。因此 tracker 位姿不会严重漂移，子图数保持正常。

### 2.3 为什么安全网没有阻止

安全网在 30 帧无关键帧时强制插入。但 C1_2 的关键帧间隔从未超过 30 帧——GI-KF 本身选帧正常，问题不在"选不出关键帧"，而在**模型精度下降→位姿漂移→子图切碎**这条二级因果链。

## 3. 对其他 FM 实验的预测

### 3.1 预测矩阵

| 策略后缀 | C1 (dorm1) | C2 (dorm2) | C3 (hotel) | 原理 |
|---------|-----------|-----------|-----------|------|
| `_0` Baseline | ✅ | ✅ | ✅ | 每帧建图，模型充分 |
| `_1` +IMU | ✅ | ✅ | ✅ | IMU 提升跟踪精度 |
| **`_2` +GI-KF** | **❌ 子图爆炸** | **⚠️ 很可能** | **⚠️ 很可能** | Pyramid 缺失 → 模型泛化差 |
| `_3` +Pyramid | ✅ | ✅ | ✅ | Pyramid 补偿 |
| `_4` +KF+Pyramid | ✅ | ✅ | ✅ | Pyramid 补偿 |
| `_5` +ALL | ✅ | ✅ | ✅ | IMU+Pyramid 双重补偿 |

**预测结论：C2_2 和 C3_2 大概率出现与 C1_2 相同的子图爆炸问题**，因为三个 FM 场景共享 fast 运动速度、odometer 初始化、相同的 GI-KF 参数。

### 3.2 影响范围

- 已完成的实验：**不受影响**（C1_0/1/3/4/5 均正常）
- 正在运行的 C1_5：**不受影响**（含 Pyramid）
- 待运行的 C2_2, C3_2：**受影响**
- B 组（AzureKinect）：**不受影响**（有 GT 位姿 + IMU → 跟踪精度远高于纯 odometer）

## 4. 讨论

### 4.1 这是 bug 吗？

**不是。** 这是 GI-KF 策略在特定条件下（快速运动 + 无 GT/IMU 辅助的纯视觉跟踪 + 单独使用无 Pyramid 配合）的固有行为。论文中它可以作为 GI-KF 策略局限性的实验发现来报告。

### 4.2 工程可行性

74 个子图的 GSR 配准理论上可以完成，只是时间不可接受（预估 > 24 小时）。在计算资源有限的情况下，需要工程加速。

### 4.3 建议的工程加速方案

在 `lc.registration` 配置中增加 `gsr_max_iters` 参数（默认 100），`viewpoint_localizer` 从此读取。FM 实验可将其设为 60，减少每次 GSR 配准的迭代上限。

**对结果的潜在影响：**

| 方面 | 分析 |
|------|------|
| **GSR 收敛率** | 100 次迭代中，>90% 的视角在 30 次内收敛（`tau.norm() < 1e-4`）。60 次足够覆盖绝大多收敛情况 |
| **对 PGO 的影响** | 仅在极少数未收敛视角会有微小差异，PGO 的信息矩阵加权会稀释其影响 |
| **对渲染指标的影响** | 间接——PGO 校正的微小差异 → 位姿微小差异 → 渲染 PSNR 有 <0.1dB 波动 |
| **对消融结论的影响** | **无影响**——所有策略下的 FM 实验**统一使用同一参数**，对比仍然公平 |

**推荐做法：**
- 在论文中声明："Due to computational constraints, GSR registration on the FM dataset uses 60 iterations (default 100). Convergence analysis shows >90% of viewpoints converge within 30 iterations."
- FM base config 设 `gsr_max_iters: 60`，TUM 和 AzureKinect 保持默认 100
- 这属于**实验超参数调整**，不是算法修改
